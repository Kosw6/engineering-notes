# 📄 Thread / Hikari 설정에 따른 Context Switching 및 Latency 분석

---

# 1. 실험 목적

본 실험은 다음을 검증하기 위해 수행하였다.

- Thread 수 증가가 CPU scheduling 및 context switching에 미치는 영향
- Hikari connection pool 크기 변화의 실질적 효과
- Context switching과 latency(p95)가 함께 변하는 패턴
- 자원 부족 상황에서 발생하는 saturation 지점 확인
- 현재 워크로드 기준 Thread / Hikari의 최적 설정 결정

---

# 2. 핵심 결과

- 기본 부하 150 RPS 비교에서 Thread 30 / Hikari 8 구간이 가장 안정적
- Stress 300 RPS의 Thread 2 / Hikari 2 구간에서 nvcswch와 p95가 함께 급증
- 기본 부하에서 Thread 60 이상은 처리량 이득 없이 cswch가 증가하는 경향 관찰
- Hikari 12 이상에서도 active thread와 cswch가 함께 증가하는 경향 관찰
- DB pending이 없는 조건에서 DB pool 부족보다 OS scheduling 비용에 가까운 병목 신호를 확인

# 5. nvcswch vs cswch 설명

### nvcswch (Involuntary Context Switching)

CPU 경쟁 상황에서 OS scheduler에 의해 강제로 발생하는 context switching이다.

특히 runnable queue 경쟁이 증가할 경우 급격히 증가하는 특징을 가진다.

본 실험에서는 Thread가 부족한 경우 runnable queue 경쟁이 심화되며
nvcswch가 급증하는 패턴이 관찰되었다.

---

### cswch (Voluntary Context Switching)

DB I/O, lock 대기 등으로 인해 thread가 스스로 CPU를 양보할 때 발생한다.

본 실험에서는:

- Thread 과다
- Hikari pool 과다
- 내부 조율 비용 증가

상황에서 cswch 증가 경향이 관찰되었다.

# 10. Hikari 내부 동작 및 Context Switching 영향 분석

HikariCP는 단순 커넥션 개수 관리가 아니라,
borrow/return 과정에서 내부 동시성 제어 구조를 가진다.

본 실험에서는 DB pending 없이도
Hikari 설정에 따라 context switching 수준 차이가 발생하는 현상이 관찰되었다.

---

## 10.1 Pool Size가 작은 경우 (Hikari 4)

* 동일 커넥션 접근 집중
* borrow/return 내부 조율 비용 증가
* thread 간 짧은 양보 증가

### 결과

* pending 없음
* cswch 증가

---

## 10.2 Pool Size가 적절한 경우 (Hikari 8)

* 커넥션 접근 분산
* hotspot 감소
* 내부 간섭 최소화

### 결과

* cswch 최소 수준 유지

---

## 10.3 Pool Size가 큰 경우 (Hikari 12~16)

* 활성 thread 수 증가
* scheduling 부담 증가
* CPU 코어 대비 runnable thread 증가

### 결과

* scheduling overhead 증가
* cswch 증가

---

## 해석

```text
Hikari 4
→ 내부 contention 증가
→ cswch 증가

Hikari 8
→ contention 완화
→ cswch 최소

Hikari 12+
→ scheduling overhead 증가
→ cswch 증가
```

즉:

> Hikari pool 역시 단순히 크게 설정하는 것이 아니라,
> context switching 비용을 최소화하는 균형 지점이 중요함을 확인하였다.

---

# 11. 종합 분석

## 1️⃣ Thread

* 최적 구간: ≈30
* 16 → 부족
* 60+ → 과다

---

## 2️⃣ Hikari

* active connection: 1~2 수준
* pending 없음
* DB 자체 병목은 관찰되지 않음

다만:

* pool이 작을 때 contention 후보 신호 증가
* pool이 클 때 scheduling overhead 후보 신호 증가

패턴이 관찰되었다.

---

## 3️⃣ Context Switching

본 실험에서는 context switching 증가가
latency 악화 구간을 설명하는 주요 병목 신호로 관찰되었다.

특히:

* Stress 300 RPS의 T2/H2에서 nvcswch와 latency 동시 급증
* 기본 150 RPS의 과다 설정 구간에서 처리량 이득 없이 cswch 증가

경향이 확인되었다.

이 결과는 여러 지표의 상관 패턴을 바탕으로 한 병목 해석이며, OS scheduling 비용이 latency 증가의 단일 원인임을 증명한 것은 아니다.

---

## 4️⃣ CPU Scheduling 관점 해석

스레드 수가 CPU 코어 수보다 과도하게 증가할 경우,
운영체제 scheduler는 runnable thread 간 CPU를 반복적으로 분배하게 된다.

이 과정에서:

* register
* program counter
* stack pointer

등 실행 문맥 저장/복원 비용이 발생한다.

특히 DB I/O workload에서는
많은 thread가 동시에 실행되더라도
실제 작업보다 scheduling 전환 비용이 더 커질 수 있다.

---

## 5️⃣ DB Connection Pool과의 관계

Thread 수 증가 시 DB 접근 요청도 함께 증가한다.

다만 본 실험에서는:

* pending 없음
* active connection 낮음

상태가 유지되었기 때문에 DB connection pool 병목 신호는 약했다.
반면 처리량 이득 없이 context switching이 증가하는 구간이 관찰되어,
현재 workload에서는 DB보다 CPU scheduling 비용에 가까운 병목 후보로 판단하였다.

그러나 향후:

* 트래픽 증가
* DB 처리량 감소
* workload 변화

상황에서는 connection pool pending이 병목으로 전환될 가능성이 존재한다.

---

# 12. 최종 결론

본 실험을 통해:

* 단순 thread 증가
* 단순 connection 증가

가 항상 성능 향상으로 이어지지 않으며,
일부 설정 구간에서 처리량 이득 없이 context switching과
latency가 함께 증가하는 패턴을 확인하였다.

현재 workload 및 시스템 자원(2 vCPU) 기준 최적 설정은:

* Max Thread Pool Size = 30
* Max HikariPool Size = 8

로 결정하였다.

---

## 핵심 결론

```text
Stress 300 RPS의 underprovisioned 설정
→ nvcswch와 latency 동시 급증
→ saturation 신호

기본 150 RPS의 과다 설정
→ 처리량 이득 없이 cswch 증가
→ scheduling overhead 후보 신호
```

따라서:

> Thread / Hikari 설정은 단순 최대 처리량 확보가 아니라,
> 현재 workload와 시스템 자원을 기준으로
> 안정적인 latency와 운영 효율을 유지하기 위한
> 유량 제어 관점에서 결정되어야 함을 확인하였다.

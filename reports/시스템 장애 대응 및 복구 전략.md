## 실시간 협업 시스템 장애 대응 및 복구 전략

### 1. 개요

본 문서는 WebSocket 기반 실시간 협업 시스템에서  
Redis, Kafka, Pub/Sub, WebSocket 서버, DB 서버 장애 발생 시  
서비스 중단을 최소화하고 정합성을 유지하기 위한 대응 전략을 정의한다.

핵심 목표는 다음과 같다.

- 실시간 처리 경로와 복구 경로를 분리
- 장애 시 전체 서비스 중단이 아닌 Degraded Mode 유지
- 복구 이후 Replay 기반 정합성 회복

---

### 2. 시스템 구성

- **WebSocket Server**
  - 클라이언트 연결 유지
  - 로컬 상태 기반 이벤트 처리
  - fanout 수행

- **Redis**
  - 실시간 상태 저장
  - 락, 편집 충돌 상태 저장

- Pub/Sub (Redis 기반)
  - 노드간 실시간 저지연 전파

- **Kafka**
  - 서버 간 이벤트 전달
  - Replay 기반 복구
  - Failback 지원

- **Database**
  - 최종 상태 저장
  - 정합성 기준 요소

---

### 3. 설계 원칙

1. **유실 방지 > 즉시 성공 응답**
2. **실시간 처리 경로와 복구 경로 분리**
3. **중복 허용 + 최종 1회 반영 (멱등성)**
4. **장애 시 기능 축소 (Degraded Mode)**
5. **복구 시 Replay + Version 기반 정합성 회복**
6. **Failover와 Fallback을 분리하여 설계**
   - 서버 장애는 failover로 처리
   - 상태 불일치는 fallback 전략으로 보정
---

### 4. 장애 유형별 대응 전략

---

#### 4.1 Redis 장애

**영향**
- 상태 유실
- 편집 상태 추적 불가

**유지 가능**
- WebSocket 연결 유지
- 로컬 서버 내 이벤트 처리

**제한 기능**
- 정합성 판단 기준 일부 상실

**대응 전략**
- Redis 상태 저장 의존 로직 → 로컬 메모리 기반 fallback
- 상태 저장 실패 시 DB에 최소 상태 기록

**복구 전략**
- Redis 복구 후 DB / Kafka 이벤트 기준 상태 재동기화

---

#### 4.2 Kafka 장애

**영향**
- 서버 간 이벤트 전달 중단
- Replay / Failback 불가

**유지 가능**
- 현재 서버 내 편집 및 락 처리
- 기본 서비스 기능 유지

**제한 기능**
- cross-node 동기화
- failback / catch-up
- 이벤트 기반 복구

**대응 전략**

Kafka는 필수 실행 경로가 아닌 보조 축으로 설계한다.

- 장애 시 Degraded Mode 진입
- 로컬 처리 중심으로 운영
- 신규 분산 처리 및 failback 제한

**유실 방지 전략**
- 이벤트는 Kafka publish 이전에 Redis 또는 DB에 저장
- publish 실패 시 재시도 가능하도록 로그/큐 유지

**복구 전략**
- Kafka 복구 후:
  - 저장된 이벤트 기반 재적재
  - Replay 수행
  - Version 기반 상태 정합성 회복

---

#### 4.3 Redis Pub/Sub 장애

**영향**
- 실시간 이벤트 전달 지연/누락

**대응 전략**
- Kafka 기반 이벤트 전달로 fallback
- 필요 시 polling 기반 보조 처리

**복구 전략**
- Pub/Sub 복구 후 정상 broadcast 재개

---

#### 4.4 WebSocket 서버 장애

**영향**
- 특정 서버 연결 클라이언트 disconnect
- 해당 노드 상태 일부 유실

**대응 전략**
- Gateway / Service Discovery 기반 재연결
- 다른 WebSocket 서버로 failover

**설계 원칙**
- 상태는 서버 로컬이 아닌 Redis / Kafka / DB 기반으로 복구 가능해야 함

**복구 전략**
- 서버 재기동 후:
  - Kafka Replay 수행
  - Redis/DB 기준 상태 복원

---

#### 4.5 Database 장애

**영향**
- 상태 저장 불가
- 정합성 기준 상실
- 커넥션 풀 고갈 및 thread blocking으로 앱 서버까지 장애가 전파될 수 있음

**대응 전략**
- DB 연결 실패 시 빠르게 실패 처리하여 장시간 대기 방지
- Circuit Breaker를 통해 일정 시간 DB 호출 차단
- 조회 기능은 Redis/캐시에 저장된 마지막 정상 상태를 기반으로 제한적으로 제공
- 쓰기 기능은 DB 직접 반영 대신 기존 Kafka/Redis 파이프라인을 통해 임시 적재
- 임시 적재된 쓰기 요청은 즉시 영속 완료로 간주하지 않고, `QUEUED` 또는 `PENDING_PERSIST` 상태로 관리
- 필요 시 다른 인스턴스에 구성된 보조 DB(임시 DB)를 활용하여 제한적으로 쓰기 요청을 수용

  - 임시 DB는 정식 고가용성 구성이 아닌 장애 완충을 위한 차선 전략으로, 자원 경쟁 및 장애 도메인 분리 한계를 가진다.

- DB 장애가 전체 서비스 중단으로 이어지지 않도록 기능별 degraded mode 적용

**복구 전략**
- DB 복구 후 Kafka/Redis에 적재된 변경 이벤트를 순차적으로 재반영
- 임시 DB를 사용한 경우, 해당 데이터도 DB와 비교하여 정합성을 맞춤
- 반영 시 idempotency key 또는 version 기반으로 중복 적용 방지
- 임시 상태를 DB와 동기화하여 정합성을 회복

---

### 5. 복구 우선순위

1. WebSocket 연결 안정화
2. 현재 세션 보호
3. 이벤트 전달 재개 (Kafka / Redis)
4. Replay / Catch-up 수행
5. Failback 수행

---

### 6. 정합성 전략

- Version 기반 상태 관리
- 발행 단계에서는 중복 이벤트를 허용하고, 소비 단계에서 Event ID 기반 멱등 처리를 통해 최종 상태는 1회만 반영

충돌 발생 시:
- Version 또는 timestamp 기반 최종 상태 결정 (충돌 해결)

---

### 7. Degraded Mode 정의

Kafka 또는 Redis 장애 발생 시, 시스템은 정상 모드에서 Degraded Mode로 전환된다.

---

**진입 조건**
- Kafka 이벤트 발행/소비 실패
- Redis 상태 저장 또는 Pub/Sub 실패
- Circuit Breaker open 상태 진입

---

**모드 전환 원칙**
- 외부 의존성(Kafka, Redis) 제거
- Gateway를 control plane으로 활용
- 로컬 처리 중심으로 서비스 유지
- 실시간 동기화보다 서비스 지속성과 입력 유실 방지를 우선
- 정합성은 복구 단계에서 보정

---

**유지 기능**
- WebSocket 연결 유지
- 동일 shard 내 local broadcast 유지
- 사용자 편집 입력 처리
- owner server 기준 단일 사용자 편집 직렬화

---

**제한 기능**
- Kafka/Redis 기반 cross-node push 이벤트 전달 중단
- shard 간 실시간 동기화 보장 불가
- replay / failback 기반 복구 일시 중단
- cross-node 충돌 감지 정확도 저하

---

**동작 방식 변화**

정상 모드:
- Redis → 상태 저장 (draft, lock)
- Kafka → cross-node 이벤트 전달
- shard 간 push 기반 실시간 동기화

Degraded Mode:
- 동일 shard 내에서는 WebSocket 기반 local broadcast 유지
- Kafka/Redis Pub/Sub 기반 서버 간 push 이벤트 전달 중단
- 클라이언트는 Gateway가 제공한 peer shard 서버 목록을 기준으로 polling하여 상태를 제한적으로 조회
- shard 간 완전한 실시간 동기화는 보장하지 않음
- 대신 owner server 직렬화와 로그 DB 테이블을 통해 정합성을 강하게 제한

---

**Gateway 역할 (Control Plane)**
- 그룹-세션-서버 매핑 정보 유지
- 각 shard 서버는 Gateway를 통해 동일 그룹의 peer 서버 위치 조회
- 클라이언트는 Gateway 정보를 기반으로 polling 대상 서버를 결정

---

**락 점유 전략 (Lock Ownership)**
- 각 엔티티는 groupId 기반으로 owner server가 결정됨
- lock acquire/release는 owner server에서만 처리하여 직렬화 보장
- 락 상태는 owner server의 로컬 세션/메모리에 유지 (TTL/heartbeat 기반)
- 전역 공유 저장소 없이 shard-local authoritative 방식으로 운영
- owner server 장애 시 기존 락은 만료된 것으로 간주하고 재획득

---

**편집 Draft 전략**
- 사용자 편집 상태(draft)는 Redis 대신 임시 DB에 저장
- draft는 baseVersion, dirtyFields, patch 기준으로 관리
- 서버 장애 시에도 사용자 입력 유실 방지
- 복구 이후 version 기반으로 상태 재정합

---

**쓰기 및 이벤트 처리 전략**
- DB 직접 반영 대신 변경 이력을 로그 DB 테이블에 기록
- 요청 상태를 `PENDING` / `DEFERRED`로 관리
- Kafka/Redis 없이 로컬 처리 중심으로 운영
- 로그 테이블은 장애 구간 동안의 상태 추적 및 복구 시 정합성 검증 기준으로 활용

---

**정합성 유지 전략 (Degraded Mode)**
- shard 간 실시간 동기화 대신 owner server 직렬화 기반으로 충돌 방지
- 로그 DB 테이블을 기준으로 변경 이력 추적
- cross-node 상태 불일치는 허용하되, 복구 이후 version 기반으로 보정

---

**복구 연계**
- 장애 해소 후:
  - Kafka Replay 수행
  - Redis 상태 재동기화
  - 로그 DB 기반 상태 검증
  - Version 기반 충돌 해결
  - Failback 수행

---

**목표**
- 전체 서비스 중단 방지
- 사용자 세션 유지
- 입력 데이터 유실 방지
- shard 단위 협업 유지
- 정합성은 복구 단계에서 회복

---

### 8. 트레이드오프

- 실시간성 vs 장애 내구성
- 단순 구조 vs 복구 복잡도
- 일부 기능 제한 vs 전체 서비스 중단

---

### 9. 결론

본 구조는 Kafka/Redis 장애 시에도 서비스 실행 경로를 유지하고,  
복구 시 Replay 및 멱등성을 통해 정합성을 회복하는 것을 목표로 한다.

즉,

**“서비스는 지속 가능하게 유지하고, 정합성은 복구 단계에서 보장한다”**

## 실시간 협업 시스템 장애 대응 및 복구 전략

### 1. 개요

본 문서는 WebSocket 기반 실시간 협업 시스템에서  
Redis, Kafka, Pub/Sub, WebSocket 서버, DB 서버 장애 발생 시  
서비스 중단을 최소화하고 정합성을 유지하기 위한 대응 전략을 정의한다.

핵심 목표는 다음과 같다.

- 실시간 처리 경로와 복구 경로를 분리
- 장애 시 전체 서비스 중단이 아닌 Degraded Mode 유지
- 복구 이후 Replay 기반 정합성 회복

---

### 2. 시스템 구성

- **WebSocket Server**
  - 클라이언트 연결 유지
  - 로컬 상태 기반 이벤트 처리
  - fanout 수행

- **Redis**
  - 실시간 상태 저장
  - 락, 편집 충돌 상태 저장
  - Pub/Sub 기반 이벤트 전달

- **Kafka**
  - 서버 간 이벤트 전달
  - Replay 기반 복구
  - Failback 지원

- **Database**
  - 최종 상태 저장
  - 정합성 기준 요소

---

### 3. 설계 원칙

1. **유실 방지 > 즉시 성공 응답**
2. **실시간 처리 경로와 복구 경로 분리**
3. **중복 허용 + 최종 1회 반영 (멱등성)**
4. **장애 시 기능 축소 (Degraded Mode)**
5. **복구 시 Replay + Version 기반 정합성 회복**

---

### 4. 장애 유형별 대응 전략

---

#### 4.1 Redis 장애

**영향**
- 실시간 상태 조회 불가
- Pub/Sub 기반 이벤트 전달 실패

**유지 가능**
- WebSocket 연결 유지
- 로컬 서버 내 이벤트 처리

**제한 기능**
- 서버 간 실시간 동기화 약화
- conflict resolution 정확도 저하

**대응 전략**
- Redis 상태 저장 의존 로직 → 로컬 메모리 기반 fallback
- Pub/Sub 실패 시 Kafka 기반 이벤트 전달로 우회
- 상태 저장 실패 시 DB에 최소 상태 기록

**복구 전략**
- Redis 복구 후 DB / Kafka 이벤트 기준 상태 재동기화

---

#### 4.2 Kafka 장애

**영향**
- 서버 간 이벤트 전달 중단
- Replay / Failback 불가

**유지 가능**
- 현재 서버 내 편집 및 락 처리
- 기본 서비스 기능 유지

**제한 기능**
- cross-node 동기화
- failback / catch-up
- 이벤트 기반 복구

**대응 전략**

Kafka는 필수 실행 경로가 아닌 보조 축으로 설계한다.

- 장애 시 Degraded Mode 진입
- 로컬 처리 중심으로 운영
- 신규 분산 처리 및 failback 제한

**유실 방지 전략**
- 이벤트는 Kafka publish 이전에 Redis 또는 DB에 저장
- publish 실패 시 재시도 가능하도록 로그/큐 유지

**복구 전략**
- Kafka 복구 후:
  - 저장된 이벤트 기반 재적재
  - Replay 수행
  - Version 기반 상태 정합성 회복

---

#### 4.3 Redis Pub/Sub 장애

**영향**
- 실시간 broadcast 지연 또는 누락

**대응 전략**
- Kafka 기반 이벤트 전달로 fallback
- 필요 시 polling 기반 보조 처리

**복구 전략**
- Pub/Sub 복구 후 정상 broadcast 재개

---

#### 4.4 WebSocket 서버 장애

**영향**
- 특정 서버 연결 클라이언트 disconnect
- 해당 노드 상태 일부 유실

**대응 전략**
- Gateway / Service Discovery 기반 재연결
- 다른 WebSocket 서버로 failover

**설계 원칙**
- 상태는 서버 로컬이 아닌 Redis / Kafka / DB 기반으로 복구 가능해야 함

**복구 전략**
- 서버 재기동 후:
  - Kafka Replay 수행
  - Redis/DB 기준 상태 복원

---

#### 4.5 Database 장애

**영향**
- 상태 저장 불가
- 정합성 기준 상실

**대응 전략**
- 쓰기 기능 제한 (강한 정책)
- 단기적으로 Redis/로컬 메모리에 임시 저장 (best-effort)

**복구 전략**
- DB 복구 후:
  - 임시 상태 reconcile
  - Version 기반 충돌 해결

---

### 5. 복구 우선순위

1. WebSocket 연결 안정화
2. 현재 세션 보호
3. 이벤트 전달 재개 (Kafka / Redis)
4. Replay / Catch-up 수행
5. Failback 수행

---

### 6. 정합성 전략

- Version 기반 상태 관리
- Event ID 기반 멱등 처리
- 중복 이벤트 허용 후 최종 상태 1회 반영

충돌 발생 시:
- 최신 version 또는 timestamp 기준으로 처리

---

### 7. Degraded Mode 정의

Kafka 또는 Redis 장애 시:

**유지**
- 로컬 편집
- WebSocket 연결

**제한**
- 서버 간 동기화
- failback / replay 기반 복구

목표:
- 전체 서비스 중단이 아닌 기능 축소

---

### 8. 트레이드오프

- 실시간성 vs 장애 내구성
- 단순 구조 vs 복구 복잡도
- 일부 기능 제한 vs 전체 서비스 중단

---

### 9. 결론

본 구조는 Kafka/Redis 장애 시에도 서비스 실행 경로를 유지하고,  
복구 시 Replay 및 멱등성을 통해 정합성을 회복하는 것을 목표로 한다.

즉,

**“서비스는 지속 가능하게 유지하고, 정합성은 복구 단계에서 보장한다”**
